<p>A preservation project for software from <a href="https://en.wikipedia.org/wiki/Norsk_Data" target="_blank" rel="noopener noreferrer">Norsk Data</a>, a Norwegian minicomputer manufacturer (1967--1998). This archive catalogs and preserves floppy disk images, with full NDFS filesystem metadata, from the NORD and ND series of minicomputers.</p>
<p><strong>Live site</strong>: <a href="https://retrocorelabs.github.io/norskdata-software-archive/" target="_blank" rel="noopener noreferrer">retrocorelabs.github.io/norskdata-software-archive</a></p>
<h2 id="readme-what-this-is">What this is</h2>
<ul>
<li>A git repository containing compressed floppy disk images (<code>.img.gz</code>) with per-image YAML metadata</li>
<li>A searchable web catalog with NDFS filesystem browsing, BPUN checksum validation, and label photo viewing</li>
<li>Import tools for adding new disk images with automatic product matching</li>
<li>Readers for the other formats these disks turn out to hold: MS-DOS (FAT12/16), SINTRAN BACKUP-SYSTEM volumes, WINCH-TO-FLOPP directory backups and tar</li>
<li>An MCP server for LLM integration with the <a href="https://github.com/RetroCoreLabs/nd100x" target="_blank" rel="noopener noreferrer">nd100x emulator</a></li>
</ul>
<h2 id="readme-architecture">Architecture</h2>
<pre><code>GitHub repo (this)              Internet Archive
  images/{md5}/                   norskdata-software collection
    image.img.gz                  (permanent binary storage)
    metadata.yaml                  stable download URLs
  collections/{product}/          shared "set" photos (one copy per product+version)
  catalog/floppies.json           generated from the YAML
  tools/ (CLI + web UI + MCP)
  site/                           generated + gitignored (GitHub Pages preview)
</code></pre>
<ul>
<li><strong>YAML per floppy is the source of truth.</strong> Each <code>.img.gz</code> has a <code>.yaml</code> file next to it with all metadata. <code>catalog/floppies.json</code>, <code>catalog/products.json</code>, <code>catalog/index.json</code> and <code>site/</code> are all <strong>generated</strong> from the YAML -- never edited by hand. <code>site/</code> is gitignored (CI rebuilds it on every push).</li>
<li><strong>Content-addressed storage.</strong> Each image lives in <code>images/{md5}/</code> -- the folder is named by the full MD5 hash of the raw image. Folders never change, even when metadata is updated.</li>
<li><strong>NDFS parsing.</strong> Every image is parsed using the <a href="https://github.com/RetroCoreLabs/norskdata-ndfs" target="_blank" rel="noopener noreferrer">norskdata-ndfs</a> library to extract volume name, boot format, user listings, and file listings.</li>
<li><strong>Floppy images in git.</strong> Images &#x3C;=1.3 MB are stored compressed in the repo. Larger artifacts (HDD images, tapes) go to Internet Archive.</li>
</ul>

<h2 id="readme-importing-floppy-images">Importing Floppy Images</h2>

<ul>

</ul>
<p>This is the recommended path: it imports <em>and</em> lets you map floppies to products (Matcher) and commit changes, all in the browser.</p>
<h3 id="readme-console-wizard-cli">Console wizard (CLI)</h3>
<pre><code class="hljs language-bash">make import-cli
</code></pre>
<p>Interactive terminal prompts for path, contributor name, and source description.</p>
<h3 id="readme-non-interactive-scripted">Non-interactive (scripted)</h3>
<pre><code class="hljs language-bash">make import-folder SRC=/path/to/folder CONTRIBUTOR=<span class="hljs-string">"Name"</span> SOURCE=<span class="hljs-string">"description"</span> RECURSIVE=1

<p>The console paths (<code>import-cli</code>, <code>import-folder</code>, <code>import-file</code>) <strong>only import</strong> -- unmatched floppies still need to be assigned to products in the web UI's Matcher. They are otherwise equivalent to the web UI: every import path leaves the catalog, search index and static site in the same state (see below).</p>
<h3 id="readme-what-happens-during-import">What happens during import</h3>
<ol>
<li>Reads the <code>.img</code> file and computes MD5 checksum</li>
<li>Parses the NDFS filesystem (volume name, boot format, users, file listings)</li>
<li>Validates BPUN checksums where applicable</li>
<li>Matches the volume name against known ND product number patterns. The match is recorded as a <em>suggestion</em> -- the floppy is left <strong>unassigned</strong> so you confirm it in the Matcher; it is not auto-linked.</li>
<li>Checks for duplicates (same MD5 = skip)</li>
<li>Compresses the image and stores it in <code>images/{md5}/</code></li>
<li>Copies label photos and transcriptions alongside the image (per-disk photos stay with the image; shared "set" photos are consolidated into the product group folder under <code>collections/</code>)</li>
<li>Generates a <code>.yaml</code> metadata file as the source of truth</li>
</ol>
<p>After the import finishes, <strong>all derived artifacts are regenerated automatically</strong> -- <code>catalog/floppies.json</code> + <code>catalog/products.json</code> (from the YAML), the <code>catalog/index.json</code> search index, and the static site in <code>site/</code>. This happens for <strong>every</strong> import path (web UI and the <code>import-*</code> CLI commands), so you never need a manual "rebuild" step. (The live GitHub Pages site is still rebuilt by CI on push; the local <code>site/</code> is just a preview.)</p>

<h2 id="readme-product-matching">Product Matching</h2>
<p>Volume names are matched against Norsk Data naming patterns:</p>






























<table><thead><tr><th>Pattern</th><th>Example</th><th>Result</th></tr></thead><tbody><tr><td><code>ND-{digits}{version}</code></td><td><code>ND-10325C</code></td><td>Product: ND-10325, Version: C</td></tr><tr><td><code>{digits}{ver}-{lang}-{disk}{density}</code></td><td><code>210691D03-NO-01S</code></td><td>Product: ND-210691, Version: D03, Disk: 1, Language: NO</td></tr><tr><td><code>N-{digits}-{digits}</code></td><td><code>N-900-188-I</code></td><td>OS distribution</td></tr><tr><td>Patch keywords</td><td><code>ND-PATCH-SIN-J</code></td><td>Patch floppy</td></tr></tbody></table>
<p>Unmatched images go through the <strong>Matcher</strong> (web UI) where you can manually assign products or create new ones.</p>

<h2 id="readme-image-organization">Image Organization</h2>
<p>Each floppy image lives in its own folder named by its full MD5 hash:</p>
<pre><code>images/
  78a2647e91efedd6c2192e24f76497c9/
    ND-10022T.img.gz                    Compressed floppy image
    ND-10022T.yaml                      Metadata (source of truth)
    DSC_0789.JPG                        Label photo
  62caae43d67b7bfedb18bf17dc079e0d/
    10079M07-NO-01S.img.gz
    10079M07-NO-01S.yaml
    DSC_0775.JPG
    labels.txt                          Label transcription
</code></pre>
<p>The YAML file contains all classification (product, version, tags). The folder structure is purely content-addressed and never changes.</p>
<p><strong>Per-disk vs. set photos.</strong> A photo whose name matches the disk (e.g. <code>ND-10022T.JPG</code>) stays in the image folder as that disk's photo. A <em>shared</em> "set" photo (one label/box photo for a whole multi-disk product) is consolidated into a product group folder, <code>collections/{product}-{version}/</code>, so it is stored once and attached to every disk in that set instead of duplicated per image.</p>

<h2 id="readme-not-every-image-is-an-nd-filesystem">Not every image is an ND filesystem</h2>
<p>A real collection contains more than ND floppies. Every image records a <code>filesystem</code> field, detected from its bytes:</p>








































<table><thead><tr><th><code>filesystem</code></th><th>What it is</th><th>What you get</th></tr></thead><tbody><tr><td><code>ndfs</code></td><td>Norsk Data filesystem</td><td>volume name, users, file listing, BPUN validation</td></tr><tr><td><code>dos</code></td><td>MS-DOS floppy, FAT12/16 (ND-OWS, NORTEXT PC material)</td><td>volume label, full directory tree, file extraction</td></tr><tr><td><code>backup</code></td><td>SINTRAN III BACKUP-SYSTEM, an ANSI-labelled volume (<code>VOL1</code>)</td><td>file names, types, dates, sizes per volume</td></tr><tr><td><code>winch</code></td><td>WINCH-TO-FLOPP, a page dump of a whole directory</td><td>directory name, "volume N of M", page map — <strong>no file names exist on the media</strong></td></tr><tr><td><code>tar</code></td><td>a tar archive written straight to the media</td><td><code>tar -tf</code> lists it directly</td></tr><tr><td><code>none</code></td><td>blank disk, failed read, or a format not recognised</td><td>raw bytes via the hex viewer</td></tr></tbody></table>
<p>An image can also be recorded as <code>ndfs</code> and carry a <code>condition: damaged</code> block: ND material is plainly in the bytes (SINTRAN <code>NAME:TYPE</code> file names survive the parity bit) but the filesystem structures cannot be read, so no file list can be produced. It is still an ND floppy and is filed as one, marked in the catalog listing and filterable there (<strong>Condition — Any / Readable / Damaged only</strong>). See <a href="https://github.com/RetroCoreLabs/norskdata-software-archive/blob/main/docs/media-condition.md" target="_blank" rel="noopener noreferrer">docs/media-condition.md</a> for how that is decided and what to expect from such a disk.</p>
<p>The 2016 bytes in front of the master block on page 0 are the boot area. Two facts are recorded about it: <code>bootFormat</code>, what it <strong>is</strong> (<code>bpun</code> for a checksum-valid BPUN block, else <code>binary</code> or <code>none</code>), and <code>bootProgram</code>, which <strong>program</strong> it carries (<code>flomon</code>, the ND floppy monitor). BPUN is a file format and FLO-MON is a program shipped in one -- see <a href="https://github.com/RetroCoreLabs/norskdata-software-archive/blob/main/docs/boot-formats.md" target="_blank" rel="noopener noreferrer">docs/boot-formats.md</a> for the field layout, the bootstrap it holds and what is still unknown.</p>
<p>Detection runs during import and can be re-run at any time — per disk or in bulk — from the Matcher, or from the command line on files that were never imported:</p>
<pre><code class="hljs language-bash">make identify PATH_=/path/to/folder ARGS=<span class="hljs-string">"--recursive"</span>
make identify PATH_=/path/to/disk.img
<span class="hljs-built_in">cd</span> tools &#x26;&#x26; node dist/cli.js identify &#x3C;file-or-folder> [--recursive] [--only dos] [--json]
</code></pre>
<pre><code>cob1.img      ndfs    1232 KB  ND    0 file(s), 1 user(s)
sib1.img      tar     1155 KB        tar archive written to the media
tools.img     dos     1155 KB        FAT12, OEM MSDOS3.3, 0 file(s), 0 dir(s), 1,167,872 B free
ND-disk-00131.img  backup  1232 KB  BACK  owner AGNETA, 52 file(s), 8 stale label(s), 1989-06-30, SINTRAN III L
</code></pre>
<p>(<code>PATH_</code>, not <code>PATH</code> — <code>PATH</code> is reserved by make.)</p>
<p>Note on BACKUP-SYSTEM volumes: the media is not erased before use, so labels from an <strong>older</strong> backup survive in areas the new run did not overwrite. Those are flagged as stale rather than mixed in with the current run.</p>
<p>The catalog lists ND floppies by default; the other kinds are one click away (<code>#/catalog?filesystem=dos</code>, <code>backup</code>, <code>winch</code>, <code>none</code>, <code>all</code>). The public site filters the same material with a <strong>Media</strong> and a <strong>Condition</strong> dropdown, and its dashboard links straight into them — a contributor row opens that contributor's floppies, the Unmatched count opens the floppies with no product assigned.</p>
<h3 id="readme-the-file-list-is-recorded-whatever-the-filesystem">The file list is recorded, whatever the filesystem</h3>
<p>Every floppy carries its contents in its YAML, so the catalog can list and search them without opening an image:</p>






























<table><thead><tr><th>filesystem</th><th>field</th><th>what is in it</th></tr></thead><tbody><tr><td><code>ndfs</code></td><td><code>ndfs.files</code>, <code>ndfs.users</code></td><td>ND file list with types, pages, BPUN validation</td></tr><tr><td><code>dos</code></td><td><code>dosFiles</code></td><td>the whole FAT tree — path (subdirectories included), size, timestamp</td></tr><tr><td><code>backup</code></td><td><code>backupFiles</code></td><td>every file the ANSI labels name, with the stale ones flagged</td></tr><tr><td><code>winch</code></td><td><em>(none possible)</em></td><td>WINCH-TO-FLOPP stores no file names on the media</td></tr></tbody></table>
<p>Searching a file name therefore finds the floppy in either front-end: <code>COMMAND.COM</code> finds MS-DOS disks, <code>TIDPLAN-INV</code> finds the BACKUP-SYSTEM volumes holding it, <code>DMAC</code> finds ND floppies. Search also matches the name the imaging gave a disk (<code>ND-disk-00283</code>), which for a floppy with no readable volume name is the only name it has.</p>
<h3 id="readme-backup-sets-many-floppies-one-backup">Backup sets: many floppies, one backup</h3>
<p>Both backup formats spread one backup over several floppies, and <code>lib/backupsets</code> puts a set back together from the catalog — no image is opened:</p>
<ul>
<li><strong>WINCH-TO-FLOPP</strong> numbers its volumes in the header, so a set is exact: <code>PACK-ONE</code> is 13 volumes, 9 held across 27 images, 6/8/9/12 missing. Each image is graded — complete, incomplete, or <code>side 0 only</code> for the one-sided read of a double-sided 8 inch disk that most of this archive's WINCH images turned out to be.</li>
<li><strong>BACKUP-SYSTEM</strong> has no volume number at all, so a run is ordered by following the file that runs off the end of one floppy onto the next (<code>ND-disk-00355</code> ends mid-file with <code>BAS-EDITOR:C</code>, <code>ND-disk-00356</code> starts with it). Where nothing continues a cut file, the chain has a break and the run is incomplete.</li>
</ul>
<p>Repeat reads of one floppy are told from genuinely different volumes by how much their listings share: measured here, reads of one disk share 74–100% of the shorter listing while different volumes of a run share at most 33%.</p>
<h3 id="readme-reads-of-one-physical-floppy">Reads of one physical floppy</h3>
<p>A floppy that reads badly was read again and again, so the archive holds several images of one disk (<code>ND-disk-00426</code>, <code>-00426b</code>, <code>-00426c</code>, <code>-00426d</code> are four attempts at disk 426). <code>lib/readgroups</code> groups them and grades each attempt — reads clean, recovered, other filesystem, damaged, no filesystem — so a bad floppy is visible as what it is: four attempts and nothing readable. The disk page in both front-ends shows the reads of that floppy; the importer UI additionally has a <strong>Reads</strong> page (<code>#/reads</code>) that lists them by physical disk and can remove a single read, every read of a disk that produced nothing, or just the failed attempts beside a good read. Removal exists only in the importer UI, never in the public catalog, and always shows the exact file list before it happens.</p>

<h3 id="readme-static-vs-dynamic-two-different-sites-for-two-different-audiences">Static vs. dynamic: two different "sites" for two different audiences</h3>
<p>There are two separate front-ends. They serve <strong>different people for different
purposes</strong>, and they work in opposite ways:</p>








































<table><thead><tr><th></th><th>Web UI (<code>localhost:3000</code>)</th><th>Static site (<code>site/</code>, GitHub Pages)</th></tr></thead><tbody><tr><td><strong>Who it's for</strong></td><td><strong>Contributors / maintainers</strong> -- the people adding and curating floppies in the repo</td><td><strong>The public</strong> -- anyone browsing the archive online</td></tr><tr><td><strong>What it's for</strong></td><td><strong>Importing and editing</strong>: scan/upload <code>.img</code> files, match them to products, review and commit changes</td><td><strong>Read-only browsing</strong>: search, view NDFS contents, look at label photos</td></tr><tr><td><strong>Where it runs</strong></td><td>Locally, on your own machine, while you work on the repo</td><td>Publicly, at the GitHub Pages URL</td></tr><tr><td>How pages are produced</td><td><strong>Dynamically</strong>, on each request, by the Express server (<code>server.ts</code>)</td><td><strong>Pre-rendered</strong> to flat <code>.html</code> files at build time by <code>static-site-builder.ts</code></td></tr><tr><td>Needs a running server?</td><td>Yes -- the Node process renders every page live</td><td>No -- it's just files served by a static host</td></tr><tr><td>Can import / edit data?</td><td>Yes (import, matcher, commit)</td><td>No -- read-only</td></tr></tbody></table>
<p>In short: the <strong>dynamic web UI is the workbench</strong> you run locally to get new floppies
into the repo; the <strong>static site is the published, read-only window</strong> onto what the
repo already contains, for public consumption on GitHub Pages.</p>
<p>GitHub Pages can only serve <strong>static files</strong> -- it cannot run server-side code. So
the builder generates the whole catalog ahead of time, including <strong>one HTML file
per product</strong> (<code>site/products/ND-XXXXX.html</code>). When you import a floppy for a new
product, the next build produces a new page for it; when a product's data changes,
its page is re-rendered and its HTML changes. This is why a build can show many
changed/added files under <code>site/</code> -- they are generated output, not hand-written.</p>
<h3 id="readme-how-the-live-site-is-deployed">How the live site is deployed</h3>
<p>The live site is <strong>built by CI from source on every push</strong>, not served from the
<code>site/</code> files in the repo. The <code>.github/workflows/pages.yml</code> workflow runs
<code>static-site-builder.ts</code> against the YAML/catalog, uploads the freshly generated
<code>site/</code> folder as the Pages artifact, and deploys that. The deploy is triggered by
changes under <code>catalog/</code>, <code>products/</code>, <code>categories/</code>, <code>images/**/*.yaml</code>, or the
builder itself.</p>
<p>Because CI regenerates <code>site/</code> from source every time, any copy of <code>site/</code> produced
locally is a throwaway build artifact -- the deployed site never uses it.</p>
<p>Locally, <code>site/</code> is <strong>rebuilt automatically after every import</strong> (web UI and CLI
alike), so the <code>:8000</code> preview stays current without a manual step. You can still
force a rebuild with <code>make static-site</code>. Product/Matcher edits made <em>after</em> an
import are reflected live on the dynamic <code>:3000</code> UI immediately; they reach the
<code>:8000</code> static preview on the next import or <code>make static-site</code>.</p>

<h2 id="readme-mcp-server">MCP Server</h2>
<p>The MCP server exposes this archive to LLMs (Claude Code, Claude Desktop, Cursor, etc.) via the <a href="https://modelcontextprotocol.io/" target="_blank" rel="noopener noreferrer">Model Context Protocol</a>. It lets an assistant search and read the catalog directly, instead of you copy-pasting data into a chat.</p>
<h3 id="readme-what-make-mcp-does">What <code>make mcp</code> does</h3>
<pre><code class="hljs language-bash">make mcp
</code></pre>
<p><code>make mcp</code> builds the tools (if needed) and runs <code>tools/dist/mcp/server.js</code>. The server:</p>
<ul>
<li>Communicates over <strong>stdio</strong> (standard input/output) using the MCP protocol -- it is <strong>not</strong> an HTTP server and prints nothing useful when run by hand. It is meant to be <strong>launched by an MCP client</strong>, not run in a terminal you watch.</li>
<li>On startup, loads <code>catalog/floppies.json</code> and <code>catalog/products.json</code> into memory, builds a search index, and resolves the ND documentation in <code>docs/nd/</code> from each product's <code>docs:</code> block.</li>
<li>Reads the archive location from the <code>ARCHIVE_ROOT</code> environment variable (defaults to the repo root). The bundled <code>.mcp.json</code> sets <code>ARCHIVE_ROOT</code> to <code>.</code>.</li>
</ul>
<p>It is <strong>read-only</strong>: it never imports, edits, or commits anything. Use the web UI (<code>make import</code>) for write operations.</p>
<h3 id="readme-tools-the-llm-can-call">Tools the LLM can call</h3>

















































<table><thead><tr><th>Tool</th><th>What it returns</th></tr></thead><tbody><tr><td><code>search_floppies</code></td><td>Full-text search across volume names, product IDs, NDFS file names, tags, and directory content. <h3 id="readme-what-an-llm-can-use-it-for">What an LLM can use it for</h3>
<ul>
<li><strong>Discovery</strong> -- "Find all floppies that contain a file named <code>SINTRAN</code>", "list every disk for product ND-210337", "which products have the most images?"</li>
<li><strong>Inspection without downloading</strong> -- read a floppy's NDFS file listing, boot format, volume name, contributor, and BPUN validation status straight from the catalog.</li>
<li><strong>Locating the actual image</strong> -- get the local path or Internet Archive URL so it (or you) can fetch the <code>.img.gz</code> for use with an emulator such as <a href="https://github.com/RetroCoreLabs/nd100x" target="_blank" rel="noopener noreferrer">nd100x</a>.</li>
<li><strong>Research questions over the whole archive</strong> -- cross-reference products, versions, languages, and file contents that would be tedious to grep by hand.</li>
</ul>
<p>It is <strong>not</strong> for adding or modifying images -- there are no write tools. Importing and product mapping stay in the web UI.</p>
<h3 id="readme-installing-it-in-an-mcp-client">Installing it in an MCP client</h3>
<p>The repo ships a pre-configured <code>.mcp.json</code> at its root:</p>
<pre><code class="hljs language-json"><span class="hljs-punctuation">{</span>
  <span class="hljs-attr">"mcpServers"</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">{</span>
    <span class="hljs-attr">"norskdata-software"</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">{</span>
      <span class="hljs-attr">"command"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"node"</span><span class="hljs-punctuation">,</span>
      <span class="hljs-attr">"args"</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">[</span><span class="hljs-string">"tools/dist/mcp/server.js"</span><span class="hljs-punctuation">]</span><span class="hljs-punctuation">,</span>
      <span class="hljs-attr">"env"</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">{</span> <span class="hljs-attr">"ARCHIVE_ROOT"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"."</span> <span class="hljs-punctuation">}</span>
    <span class="hljs-punctuation">}</span>
  <span class="hljs-punctuation">}</span>
<span class="hljs-punctuation">}</span>
</code></pre>
<p><strong>Prerequisite (once):</strong> build the tools so <code>tools/dist/mcp/server.js</code> exists:</p>
<pre><code class="hljs language-bash">make setup
</code></pre>
<p><strong>Claude Code</strong> -- run inside the repo so it picks up <code>.mcp.json</code> automatically:</p>
<pre><code class="hljs language-bash"><span class="hljs-built_in">cd</span> norskdata-software-archive
claude          <span class="hljs-comment"># Claude Code reads ./.mcp.json and offers the "norskdata-software" server</span>
</code></pre>
<p>The <code>args</code> path is relative to the repo root, so launch Claude Code from there. To register it explicitly (or from elsewhere), use an absolute path:</p>
<pre><code class="hljs language-bash">claude mcp add norskdata-software \
  --<span class="hljs-built_in">env</span> ARCHIVE_ROOT=/abs/path/to/norskdata-software-archive \
  -- node /abs/path/to/norskdata-software-archive/tools/dist/mcp/server.js
</code></pre>
<p>Verify with <code>claude mcp list</code>, or ask Claude something like <em>"Use the norskdata archive to list the products with the most floppy images."</em></p>
<p><strong>Claude Desktop / Cursor / other clients</strong> -- add the same block to that client's MCP config (for Claude Desktop, <code>claude_desktop_config.json</code>), using <strong>absolute paths</strong> for <code>args</code> and <code>ARCHIVE_ROOT</code> since those clients don't run from the repo directory. Restart the client afterwards.</p>
<blockquote>
<p>The client starts the server itself -- you do <strong>not</strong> need to keep <code>make mcp</code> running. <code>make mcp</code> is only for manually testing that the server boots.</p>
</blockquote>
